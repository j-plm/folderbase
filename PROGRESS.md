## Decisions & Notes

- Physical files are never moved by virtual folder operations — all organisation is metadata-only
- `files.metadata` is a JSON blob; SQLite JSON functions used for querying
- All primary keys are `TEXT` UUIDs generated in Rust
- Single root `CLAUDE.md` rather than per-directory files — revisit if Rust and frontend contexts grow large
- Replaced `tauri-plugin-sql` with direct `sqlx` pool managed as Tauri state — cleaner for Rust-side commands; all DB access from frontend goes through `invoke()`
- `UNIQUE INDEX` on `files.file_path` enforces deduplication; `INSERT OR IGNORE` silently skips already-ingested files
- Times live inside Date values rather than in a Time type (as Notion, Airtable and Lightroom do): sorting needs the day anyway, and "time of day" is better as a grouping than a stored property. Clock times from file names and EXIF stay zoneless (floating); Created/Modified are UTC instants converted to local for display and comparison
- Property bootstrapping uses `infer_value_type` heuristic: RFC3339/ISO-8601 values (with or without a time) → "date", >20 distinct values → "free_text", otherwise → "enum"
- `DatabaseView.tsx` is dead code — `MainPane` renders `LocationDatabaseView` exclusively; edits to `DatabaseView.tsx` have no effect
- `.gitignore` excludes `node_modules/`, `dist/`, `src-tauri/target/`, `.DS_Store`; repo pushed to https://github.com/j-plm/folderbase (2026-10-13)
- Source tags (`files.tags`) are derived from the path on every refresh and never edited; "covered" is computed per row as "the value appears in any of the file's properties". Tag promotion is a folder mapping, so it persists through refresh
- Folder mapping onto a Multi-select appends and is re-applied on every refresh, so removing a mapped value by hand from one file comes back on the next refresh — unmap the folder instead
- A view's folder structure lives in its `location_views.definition` as `folders`, beside `table`, rather than in `views` / `view_nodes` (which stay unwired): it's per location view, so the view's filters decide its files, and it saves, drafts and reverts with the rest of the view. Folder membership is worked out in TS (`lib/folderTree.ts`), not Rust, so it always matches the Database view's filters, patterns and implied scope values. Branches are keyed by folder value (a month by "YYYY-MM"); Database grouping stays separate, but can seed the structure
- Saved views (`location_views`, per location) are separate from the virtual-folder `views` / `view_nodes` tables for now. A view's `definition` is `{ "table": … }`, so a folder presentation with its own movable layers can sit beside it later. Database grouping is deliberately not treated as folder layers. Each location has one default view that saves as it changes; named views keep unsaved edits in `draft` (shown as "— Edited") until Save Changes / Revert Changes. Search, selection and folded groups aren't part of a view. Column widths stay per location in local storage
- `files.metadata` blob is for user-defined and EXIF properties only — filesystem fields (`file_name`, `extension`, `size_bytes`, `created_at`) belong in dedicated columns; `get_location_properties` reads keys from the blob directly, so anything written there surfaces as a user-visible column
